## 1. 功能概述

语音频道支持两种模式：**自由讨论（FREE_DISCUSSION）** 与 **舞台（STAGE）**（11 §2.1）。自由讨论即普通语音频道（见文档 09）；舞台模式将成员分为 **台上发言者（SPEAKER）** 与 **听众（AUDIENCE）**，并引入 **举手申请队列（QUEUED）** 与管理/协管的 **抱上/抱下** 操作——交互整体对标 Discord Stage Channel（Request to Speak / Invite to Speak / Move to Audience）与 KOOK 舞台的麦序管理。

关键服务端约束（客户端必须正确呈现）：

- 台上人数：`max_speakers ∈ [1, 50]` 可配，**默认 20（软限），硬顶 50**（11 AA.1；07 专项 3.2 修订 06 的「最多 20」）。
- **频道人数 > 50 强制 STAGE**，且 >50 时禁止切回 FREE（11 Y.4、Z.2）。
- 超额自动禁说：**第 51 人及之后按进房顺序自动禁说（可听）**，来源标记 `CAPACITY_QUEUE`，有人离开按 FIFO 解除，被禁说者自动进入申请队列尾部（11 Z.3–Z.6）。
- 舞台角色与队列的**权威在 Owl-Server**，SFU 只认 caps（11 §1）；客户端一切台上/台下渲染以 Gateway 事件为准。
- **无服务端主咖位**：只听主咖等听感由客户端退订实现（11 AE.2、07 专项 3.3）。

## 2. 用户故事 / 使用场景

| # | 用户故事 |
|---|----------|
| US-1 | 作为频道管理员，我在频道设置里把语音频道切为舞台模式，设定台上名额 5，用于讲座。 |
| US-2 | 作为听众，我进入舞台频道后默认闭麦，能听到全部台上发言者，界面清晰区分台上/听众区（对标 Discord Stage 的 Speakers/Audience 分区）。 |

## 3. 功能需求明细（FR）

### 3.1 模式与频道配置

| 编号 | 需求 | 验收口径 |
|------|------|----------|
| FR-01 | 频道设置页提供模式切换（自由讨论 / 舞台），走 `PATCH /channels/{id}/voice-stage`（11 AE 8.1）。可见性：服管/有频道管理或 `STAGE_CHANGE_MODE` 节点者；协管默认可改，但受 `allow_co_mod_change_mode` 开关约束（11 Y.2）——开关关闭时协管端该入口隐藏或禁用并附说明。 | 权限矩阵通过 |
| FR-02 | 配置项：`mode`、`max_speakers`（1–50，默认 20）、`request_to_speak_enabled`、协管列表 `co_moderator_ids`、`allow_co_mod_change_mode`。`max_speakers` 设为 21–50 时允许保存但 UI 黄色警告「超过推荐上限 20，可能影响听众带宽」（11 AA.2）。 | 21–50 有警告仍可存 |
| FR-03 | FREE→STAGE 切换：客户端提示「切换后仅台上成员可发言」。若当前可说话人数 > `max_speakers`，服务端按开麦更久者优先留台，其余变听众（11 Y.3）——被下台者客户端收到状态变化后 toast「频道已切换为舞台模式，你已进入听众席」。 | 被下台者有提示 |
| FR-04 | STAGE→FREE 切换：服务端将清空申请队列（11 Y.4），客户端切换前确认弹窗需注明「当前申请队列将被清空」。当前人数 > 50 时该操作被服务端拒绝（错误码如 `STAGE_REQUIRED_BY_CAPACITY`，11 §10.3），客户端切换按钮置灰并提示「人数超过 50，无法切回自由讨论」。 | >50 时置灰 |
| FR-05 | 人数降回 ≤50 后**不自动**回 FREE（11 Y.5），客户端不得自行渲染回自由模式，一切以 `STAGE_INSTANCE_UPDATE` / 频道配置事件为准。 | 状态跟随服务端 |

### 3.3 举手申请（Request to Speak）

| 编号 | 需求 | 验收口径 |
|------|------|----------|
| FR-10 | 听众底部操作栏提供「举手」按钮（对标 Discord Request to Speak 手型图标）→ `POST /channels/{id}/stage/apply`；再次点击取消 → `DELETE .../stage/apply`。重复申请服务端幂等保位（11 AB.8），客户端防抖即可。 | 申请/取消可用 |
| FR-11 | 可申请条件（11 AB.2）：在频道内、非 SPEAKER、未被禁申请、`request_to_speak_enabled=true`。任一不满足则按钮隐藏或禁用并给原因文案；`request_to_speak_enabled=false`（仅抱麦模式，11 AB.3、07 专项 3.4）时显示「本频道由管理员邀请上麦」。 | 各态文案正确 |
| FR-12 | 队列展示：全员可见 **简表**（昵称/头像/序号，11 AE.1）；管理/协管可见扩展字段（申请时间、来源 `USER_APPLY|CAPACITY_QUEUE|ADMIN`）。队列数据来自 `STAGE_QUEUE_UPDATE` 事件，FIFO 顺序渲染。 | 两档可见性 |
| FR-13 | 队列上限 100（11 AB.7）：满时申请接口报错，客户端提示「申请队列已满，请稍后再试」。 | 有独立文案 |
| FR-14 | 队列条目 30 分钟未处理过期（11 AC.2）：客户端收到自己被移出队列的事件后提示「举手已过期，可重新申请」。 | 过期有提示 |

### 3.4 抱上 / 抱下 / 下麦

| 编号 | 需求 | 验收口径 |
|------|------|----------|
| FR-15 | 管理/协管在队列面板对条目操作「上麦」（`POST .../stage/bring-up { user_id }`）/「移出队列」；也可对任意听众**直抱**不经队列（11 AB.9）——右键听众 →「邀请上台」。 | 直抱可用 |
| FR-16 | 台上已满时抱上被服务端拒绝（11 AA.3）：客户端预先在满员时将「上麦」按钮置灰提示「台上名额已满，请先移下他人」；若竞态导致仍收到拒绝错误则 toast 同文案。 | 前置置灰 + 兜底 |
| FR-17 | 抱下：右键台上成员 →「移至听众席」（`POST .../stage/bring-down`）。被抱下者变 AUDIENCE、停止发布、**不回队列**（11 AB.5），其客户端 toast「你已被移至听众席」。**抱下与静音必须是分开的菜单项与 API**（11 AD.5），禁止合并。 | 菜单分离 |
| FR-18 | 被抱上的用户端：收到 `stage_role=SPEAKER` + `caps_updated` 含 `publish_audio` 后，弹显著提示「你已被邀请上台，麦克风已可用」并默认保持 self_mute 由用户自行开麦（对标 Discord：上台后仍需自己解除静音）。 | 不自动开麦 |
| FR-19 | 主动下麦：台上用户点「下麦」→ `POST .../stage/self-leave` → 变 AUDIENCE 释放槽位（11 AB.6）。 | 槽位计数回落 |
| FR-20 | 断线保留：SPEAKER/QUEUED 断线 60s 内保留席位（11 AC.3），客户端重连成功后按服务端回放的 stage_role 与 caps 恢复渲染，不主动清空自己的台上状态。 | 60s 内重连回台 |

### 3.5 >50 强制舞台与容量禁说（CAPACITY_QUEUE）

| 编号 | 需求 | 验收口径 |
|------|------|----------|
| FR-21 | 频道 connected 人数 > 50 时服务端强制 `mode=STAGE`（11 Z.2）：全员客户端收到模式变更事件后切换舞台布局，并 toast「频道人数超过 50，已自动进入舞台模式」。 | 自动切布局 |
| FR-22 | 第 51 人及之后进房者被容量自动禁说（可听，11 Z.3）：其客户端根据 VOICE_STATE/CAPS 事件中的来源标记 `CAPACITY_QUEUE`（11 Z.4）显示专属横幅「频道人数较多，你当前为仅收听状态，已自动加入上麦申请队列（第 N 位）」；麦克风按钮禁用态使用**区别于服务器静音**的样式/文案。 | 来源可区分 |
| FR-23 | 容量禁说者自动入申请队列尾部（11 Z.6）：客户端在队列中正常显示这些条目（管理端可见来源 CAPACITY_QUEUE 标签），并允许管理抱上（抱上即解除有效禁说，11 AD.1.4）。 | 队列含容量项 |
| FR-24 | 释放解除：有人离开后 FIFO 解除最早被容量禁说者（11 Z.5）。被解除者客户端 toast「人数已回落，你的收听限制已解除」；注意解除 ≠ 自动成为 SPEAKER（11 §3.2），STAGE 下仍需申请/抱麦，客户端文案不得暗示可直接发言。 | 提示语义准确 |
| FR-25 | 大房禁止自由上麦（07 专项 3.4）：STAGE 下无任何「自己开麦即说」路径，麦克风按钮对 AUDIENCE/QUEUED 始终禁用，悬浮提示「舞台模式下需上台后才能发言」。 | 无旁路 |

## 4. UI / UX 要求

1. **对标 Discord Stage**：台上大卡片 + 听众小头像墙；举手按钮为手型图标常驻底栏；被邀请上台使用全屏级醒目弹层（接受后仍需手动开麦）。
2. **对标 KOOK 舞台**：队列面板支持管理侧一键「上麦」，队列序号明确可见；协管任命入口在频道设置内。
3. **状态色规范**：SPEAKER 边框主题色；QUEUED 举手黄色角标；capacity_muted 蓝灰色「仅收听」标签；server_mute 红色。四种来源（自我/服务器/Restriction/CAPACITY_QUEUE）图标与文案必须可区分（11 §6.1 附加标志、07 专项 4 注意 2）。
4. **队列面板**：右侧抽屉，管理视图每行含头像、昵称、来源标签、等待时长、[上麦] [移除] 按钮；普通成员视图只读简表。
5. **提示与动效**：上台/下台有轻量过渡动画；抱下、容量禁说、解除禁说均有 toast；所有 toast 同时进入频道内系统消息流以便回溯。
6. **空态**：台上无人时显示「暂无发言者」占位与（对管理）「邀请成员上台」引导。
7. **防误操作**：抱下、清空队列需二次确认；模式切换确认弹窗列出后果（清队列/留台规则）。

## 5. 与服务端 / SFU 的交互

### 5.1 REST（11 AE 8.1）

| 接口 | 客户端使用场景 |
|------|----------------|
| `PATCH /channels/{id}/voice-stage` | 频道设置页保存 mode / max_speakers / 开关 / 协管 |
| `POST /channels/{id}/stage/apply` | 举手 |
| `DELETE /channels/{id}/stage/apply` | 取消举手 |
| `POST /channels/{id}/stage/bring-up` | 抱上（队列面板 / 直抱菜单） |
| `POST /channels/{id}/stage/bring-down` | 抱下 |
| `POST /channels/{id}/stage/self-leave` | 主动下麦 |

### 5.2 事件流

| 事件 | 客户端处理 |
|------|-----------|
| `VOICE_STATE_UPDATE`（含 `stage_role` 与 mute 标志） | 更新台上/听众/队列角标、自身横幅 |
| `STAGE_QUEUE_UPDATE`（全员简表） | 重绘队列面板与「第 N 位」 |
| `STAGE_INSTANCE_UPDATE` / 频道配置更新 | 模式、max_speakers、开关变化 → 布局与入口刷新 |
| SFU `caps_updated` | 发言能力实际生效点：含 `publish_audio` 才允许开麦发送（Caps 投影见 11 AD.4） |
| SFU `speaking` | 台上说话高亮 |

### 5.3 关键时序：听众上麦

```text
听众A                 Owl-Server                Owl-SFU            协管B
 │ POST stage/apply ──►│ 入队 FIFO                                   │
 │ ◄─ STAGE_QUEUE_UPDATE（全员广播，A 见第 N 位） ────────────────────►│
 │                     │ ◄──────────────── POST stage/bring-up {A} ──│
 │                     │ A: QUEUED→SPEAKER，占槽，重算 caps            │
 │                     │ UpdateParticipantCaps(A, +publish_audio) ──►│
 │ ◄─ VOICE_STATE_UPDATE(stage_role=SPEAKER)                        │
 │ ◄─────────────────── {"op":"caps_updated","d":{caps:[…publish_audio]}}
 │ UI：上台提示；用户手动开麦后开始发布                                  │
```

抱下 / 服务器静音的差异（11 AD.5）：抱下走 bring-down → stage_role 变 AUDIENCE 且 caps 去 publish；服务器静音仅 caps 去 publish、stage_role 仍为 SPEAKER——客户端两者渲染必须不同。

### 5.4 与迁移的协作（11 AF）

热迁移保留 SPEAKER/QUEUED/队列序/capacity 标志，迁入新节点后 SFU 重发 caps；客户端在迁移期间**不清空**舞台状态，仅按迁后事件校正。

## 6. 边界与异常情况

1. **竞态：满员瞬间抱上** — 以服务端拒绝为准（AA.3），客户端 toast 并刷新台上计数。
2. **模式切换与举手竞态** — STAGE→FREE 后收到的残留队列事件直接丢弃；以最新 `STAGE_INSTANCE_UPDATE` 为准。
3. **capacity_muted 与 QUEUED 并存**（11 §6.1）— 客户端需同时渲染「仅收听」标签与队列序号，不互斥。
4. **SPEAKER 断线 60s 边界** — 重连后若服务端已释放席位（>60s），以回放的 stage_role=AUDIENCE 为准，提示「台上席位已释放」。
5. **协管权限被撤** — 收到成员/角色事件后即时收起管理入口；进行中的操作被服务端 403 时 toast「权限已变更」。
6. **>50 强制 STAGE 期间的第 50/51 人边界** — 人数统计以 Server VoiceState 为准（11 Z.7），客户端不自行判定谁是「第 51 人」，只渲染事件下发的标记。
7. **举手后离开频道** — 离房即出队；重进不恢复队位（须重新申请），客户端不缓存旧队位。
8. **关闭码交互** — 舞台频道内的信令关闭码处理与文档 09 §6.1 完全一致；`CAP_DENIED` 在舞台语境下额外检查是否因失去 join 资格（如频道级 Restriction）。

## 7. 验收标准

1. 模式切换、举手、抱上、抱下、下麦全链路联调通过，caps 生效延迟端到端 < 1s（对齐 05 §7.4）。

3. 模拟 60 人进房：第 51–60 人全部出现 CAPACITY_QUEUE 横幅并自动入队；随机离开 5 人后按进入顺序恰好 5 人解除并收到提示。
4. >50 时切回 FREE 被拒且按钮置灰；人数降至 45 不自动回 FREE。

6. 只听主咖：退订 19/20 路后 SFU 侧转发路数对应下降（服务端指标核验）。

9. 协管四个权限节点逐一撤销后对应入口消失，无越权请求发出。
