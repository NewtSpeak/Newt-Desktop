## 1. 功能概述

屏幕共享允许语音频道内符合条件的成员将整个屏幕、单个窗口或应用画面共享给同频道成员观看，交互对标 Discord Go Live（底部面板「共享屏幕」按钮 → 来源选择器 → 质量档位 → 上线；观看端点击「观看」加入某路流）与 KOOK 屏幕分享。

媒体路径：屏幕轨与音频一样经 **Newt-SFU 选路转发**，不走客户端 Mesh，也**不经 Newt-Server 转 RTP**（14 §1、07 5C.3）。发起共享必须先经 **Newt-Server 审批**（RBAC + 舞台角色 + 配额预留），Server 刷新 Media Token 使 caps 包含 **`publish_screen`** 后，客户端才可向 SFU 发布屏幕轨（14 BC.1）。

核心约束：

- 权限位：`STREAM`（发起）、`STREAM_QUALITY`（更高清晰度档）、`STREAM_END_OTHERS`（结束他人，独立权限）（14 BE）。
- 舞台/大房仅台上（SPEAKER）可共享，听众不可（14 AX.1、07 5C.2）；FREE 模式在频道内 + 有 `STREAM` 即可（AX.2）。
- 每用户同时 1 路（AX.4）。
- 配额：服基准默认 3、频道默认 2，实际允许 = min(频道剩余, 服有效剩余)；系统管可开动态降额，有效上限随负载下降且永不超过基准（14 AY）。
- 质量档：480p / 720p / 1080p，帧率约 5–30；SFU 不转码，降质靠客户端 simulcast/选层（14 BA）。

## 2. 用户故事 / 使用场景

| # | 用户故事 |
|---|----------|
| US-1 | 作为语音频道成员，我点击底部面板「共享屏幕」，在选择器中挑选整屏或某窗口，选择 720p/30fps，点击「开始直播」，频道内我的头像出现 Live 角标（对标 Discord Go Live）。 |
| US-2 | 作为观众，我看到成员卡片上的「直播中」标记，点击「观看」进入播放视图，可放大到全屏或弹出独立窗口。 |

| US-6 | 作为正在共享的用户，服务器负载升高触发动态降额且策略配置为掐最早，我的共享被系统结束，我收到明确原因提示「因服务器负载，你的共享已被系统结束」。 |

| US-10 | 作为观众，我希望听到共享者的系统声音（如放视频）——见「依赖服务端待补充」。 |

## 3. 功能需求明细（FR）

### 3.1 发起与停止

| 编号 | 需求 | 验收口径 |
|------|------|----------|
| FR-01 | 入口：底部语音面板「共享屏幕」按钮，仅在已连接语音时可用。可用性前置判断（本地）：具备 `STREAM`；STAGE 模式下 `stage_role=SPEAKER` 且未被 server_mute/禁说（14 AX.1）；当前无自己的活跃共享（AX.4）。不满足时按钮禁用 + 悬浮原因。 | 各不满足态有原因文案 |
| FR-02 | 来源选择器（对标 Discord）：Tab 分「屏幕」（多显示器逐个列出缩略图）与「窗口/应用」（枚举可捕获窗口缩略图，含应用图标）；macOS 首次使用引导开启「屏幕录制」系统权限。 | 双 Tab + 缩略图 |
| FR-03 | 质量选择：分辨率档 480p / 720p / 1080p 与帧率档（如 15 / 30；范围 5–30，14 BA.1）。超出用户 `STREAM_QUALITY` 允许档的选项置灰并注明；默认档取服务端下发的展示策略默认值（14 BC.5），无下发时默认 720p/30。 | 越权档不可选 |
| FR-04 | 发起流程严格按 14 BC.1：`POST /channels/{id}/voice/screen/start { quality? }` → 成功后 Server 刷新/签发含 `publish_screen` 的新 token → 客户端以 `auth` 帧在位更新 token（协议 §2.3.3）→ 通过既有 PeerConnection renegotiation 发布屏幕轨（客户端发 `offer` 含新增视频轨，收 `answer`）→ SFU 校验 caps 上报 → Server 置 ACTIVE 并广播 `SCREEN_SHARE_START`。 | 时序与 BC.1 一致 |
| FR-05 | 发布成功前为 RESERVED 占坑态（14 AZ.4）：客户端在 start 返回后若采集/协商失败，必须调用 stop 主动释放预留，避免占坑到超时。 | 失败即释放 |
| FR-06 | 停止：本人点「停止共享」→ `POST .../screen/stop` + 移除本地轨；收到 `SCREEN_SHARE_STOP` 后清理 UI。共享的窗口被关闭/显示器拔出时自动触发停止。 | 停止路径完整 |
| FR-07 | 被动停止：处理 `SCREEN_SHARE_STOP` 的全部 reason（14 §8）：`self`（无提示）/ `admin`（「你的共享已被管理员结束」）/ `demote`（「你已离开台上，共享已停止」）/ `quota`（「因服务器负载，共享已被系统结束」）/ `disconnect`。每个 reason 独立文案。 | 逐 reason 验收 |
| FR-08 | 自己共享中的 UI：底部面板按钮变为高亮「正在共享」，点击弹出面板含预览小窗、更改质量、停止按钮（对标 Discord 直播中面板）；系统级提示条/边框标明正在共享（防泄露误播）。 | 直播中面板齐全 |

### 3.2 权限与舞台联动

| 编号 | 需求 | 验收口径 |
|------|------|----------|
| FR-09 | 服务端错误码逐一处理（14 §9）：`STREAM_PERMISSION`（无权限）、`STAGE_SPEAKER_REQUIRED`（舞台下非台上）、`NOT_IN_VOICE`、`SCREEN_QUOTA_EXCEEDED`、`SCREEN_ALREADY_ACTIVE`、`SCREEN_QUALITY_NOT_ALLOWED`——各自独立中文文案，其中 QUOTA 提示附当前占用/上限。 | 六错误码全覆盖 |
| FR-10 | 抱下/失去 SPEAKER → 服务端自动结束共享（14 BB.1）：客户端收到 stage_role 变化与 SCREEN_SHARE_STOP(demote) 后立即停采集并清理，不做「恢复共享」重试。 | 不自动重开 |
| FR-11 | FREE 模式离开语音频道 → 共享随之结束（14 BB 注）；切换频道不携带共享，需在新频道重新发起。 | 切频道共享终止 |
| FR-12 | caps 校验兜底：即使 UI 判断可共享，最终以 start 接口与 `caps_updated` 是否含 `publish_screen` 为准；收到去除 `publish_screen` 的 `caps_updated` 时立即停止发布。 | caps 驱动停止 |

### 3.3 配额的前置提示与被动降额

| FR-15 | 动态降额（14 AZ.3）：有效上限下调导致「拒新」——客户端刷新配额显示并在按钮提示注明「服务器负载较高，共享名额暂时下调」；若温和策略掐掉最早共享，被掐者按 FR-07 quota 文案处理，观看者视图提示「该共享已结束」。 | 两分支均验证 |

## 4. UI / UX 要求

1. **对标 Discord Go Live**：入口按钮（屏幕 + 箭头图标）→ 选择器弹窗（来源 Tab + 质量下拉 + 「开始直播」主按钮）→ 成员卡片 Live 红色角标 → 观看按钮。
2. **对标 KOOK**：频道内共享者列表置顶展示；观看人数计数显示在共享卡片上（若服务端提供，见待补充）。
3. **配额提示前置化**：任何会失败的点击都应在点击前可预期——按钮禁用态 + 悬浮原因是第一道，服务端错误码 toast 是兜底。
4. **质量档位选择器**：三档 + 帧率组合，越权档置灰并附「需要 STREAM_QUALITY 权限/更高身份组」说明文案（文案可由服务端展示策略下发，14 BC.5）。
5. **观看视图控件**：底部悬浮条（音量、全屏、弹出、选层、关闭），3s 无操作自动隐藏。
6. **共享中防误播**：正在共享时切换共享源需经确认；停止共享放在明显位置且不与「断开语音」相邻防误触。
7. **无障碍与国际化**：所有 reason 文案集中管理；色盲友好的 Live 角标（红色 + 「LIVE」文字双编码）。

## 5. 与服务端 / SFU 的交互

### 5.1 发起时序（14 BC.1 + 协议 §2）

```text
Client                        Newt-Server                        Newt-SFU
  │ 1. POST /channels/{id}/voice/screen/start {quality:"720p"}
  │ ────────────────────────►│ RBAC STREAM + 舞台角色 + Restriction
  │                          │ 配额预留（ScreenSlot RESERVED）
  │                          │ 刷新 token：caps ⊇ publish_screen
  │ ◄── 200 {token, reservation…}
  │ 2. {"op":"auth","d":{token}} 在位更新 ────────────────────────►│
  │ 3. 采集屏幕轨 → {"op":"offer"}（renegotiation 加视频轨） ───────►│
  │ ◄── {"op":"answer"}                                           │
  │ ═══ 屏幕轨发布 ═══════════════════════════════════════════════►│ 校验 caps
  │                          │ ◄──── track active 上报 ────────────│
  │                          │ RESERVED → ACTIVE
  │ ◄── Gateway: SCREEN_SHARE_START（全频道广播） 
  │ 观众：subscribe(该路) → SFU offer 加下行轨 → 观众 answer → 收流
```

结束：`POST .../screen/stop` 或 track ended / 抱下 / 超时 → Server 释配额 → 广播 `SCREEN_SHARE_STOP{reason}`。

### 5.2 相关信令与事件对照

| 通道 | 消息 | 用途 |
|------|------|------|
| SFU WSS | `track_published/track_ended {user_id, kind}` | 屏幕轨出现/消失（kind 区分音频/视频） |
| SFU WSS | `caps_updated` | `publish_screen` 授予/回收 |
| SFU WSS | `subscribe` / `unsubscribe` | 观看端按需拉流/停看 |
| Gateway | `SCREEN_SHARE_START/STOP`、`SCREEN_QUOTA_UPDATE`、`VOICE_STATE_UPDATE(self_stream)` | 业务层展示与配额 |
| REST | `screen/start`、`screen/stop`、`GET /guilds/{id}/screen-quota` | 审批、停止、配额查询 |

### 5.3 客户端共享状态机

```text
IDLE ──点击共享+本地前置通过──► REQUESTING (POST screen/start)
REQUESTING ──200──► CAPTURING (系统采集授权/取源)
REQUESTING ──错误码──► IDLE (toast 对应文案)
CAPTURING ──采集成功──► PUBLISHING (auth 在位更新 + renegotiate)
CAPTURING ──采集失败/用户取消──► IDLE (调用 stop 释放 RESERVED)
PUBLISHING ──track active + SCREEN_SHARE_START──► LIVE
LIVE ──本人停止/窗口关闭──► STOPPING (POST screen/stop) ──► IDLE
LIVE ──SCREEN_SHARE_STOP(admin/demote/quota)──► IDLE (按 reason 提示)
LIVE ──信令断开──► RECONNECTING (60s 内恢复回 LIVE，超时 IDLE)
```

任何状态收到 `caps_updated` 去除 `publish_screen` → 立即停采集回 IDLE。

### 5.4 断线与迁移（14 BB）

- 断线 60s 内重连：配额与会话意图保留（BB.4），客户端重连成功后尝试恢复发布（token 仍含 publish_screen 则直接 renegotiate 重发轨）；超 60s 以服务端释放为准，提示需重新发起。
- 热迁移：音画同迁（BB.2），客户端在新节点按迁移流程重建后恢复 `publish_screen` 发布，观看端自动重订。

## 6. 边界与异常情况

1. **start 成功但采集失败**（用户在系统权限弹窗点了拒绝）：立即调用 stop 释放 RESERVED（FR-05），并引导去系统设置授权。
2. **竞态：两人同时抢最后一个名额**：以服务端为准，后到者收 `SCREEN_QUOTA_EXCEEDED`；客户端配额缓存以事件为准刷新，不做本地扣减权威。
3. **观看中共享者迁移/重协商**：观看端画面短暂冻结属可接受，超 5s 无帧显示「重新连接中」占位。
4. **1080p 高负载**：收到 `SCREEN_QUALITY_NOT_ALLOWED` 或配额事件表明最高档被压低（14 BA.2）时，发起面板动态收窄可选档。
5. **多显示器热插拔**：共享的显示器被移除 → 自动停止并提示；选择器实时刷新来源列表。
6. **关闭码**：共享期间信令 `closed` 处理与文档 09 §6.1 完全一致；`NODE_DRAINING` 迁移期间共享意图保留（BB.2/BB.4），迁后自动恢复，失败则提示重新发起。
7. **每用户 1 路**：本端已有共享时再点入口直接切到「正在共享」面板而非报错；多端同账号第二路以服务端 `SCREEN_ALREADY_ACTIVE` 为准。
8. **观看端订阅失败**：subscribe 后 5s 未收到对应下行轨（SFU offer），重试一次；仍失败提示「加载直播失败」并回到频道视图。
9. **配额事件丢失**：客户端配额缓存超过 60s 未收到更新时，进入发起流程前主动 `GET /guilds/{id}/screen-quota` 兜底刷新，防止基于陈旧数据前置放行。
10. **深色/多显示器 HDR 内容**：颜色空间转换按平台默认处理，客户端不承诺 HDR 透传；发现明显偏色时提示用户切换 SDR。
11. **通话中被服务器 deafen**：仅影响音频下行，观看画面继续；UI 提示「你已被禁听，仅可观看画面」。

## 7. 验收标准

1. 发起时序抓包与 14 BC.1 六步一致；token 在位更新（auth 帧）期间音频不中断。
2. 六个错误码 + 五个 stop reason 逐一注入测试，文案与行为符合矩阵。
3. STAGE 下 AUDIENCE/QUEUED 无发起入口；SPEAKER 被抱下后共享 1s 内自动结束且不重试。
4. 配额场景：频道 2/2 满时前置拦截；服有效上限动态从 3 降到 1 时按钮提示更新 <3s；温和掐流被掐者收到 quota 文案。
5. 观看端未点观看时无该路下行流量（抓包核验）；停止观看后订阅剪枝生效。
6. 三档质量 × 有/无 `STREAM_QUALITY` 组合验证；越权请求被 `SCREEN_QUALITY_NOT_ALLOWED` 拒绝且客户端本不应发出。
7. 多路（3 路）共享切换与 4 路网格同看功能可用，切换 <1s 出画。
8. 断线 55s 重连恢复共享成功；65s 后重连提示重新发起。
9. macOS 屏幕录制权限引导流程、窗口关闭自动停止、来源热插拔刷新全部通过手测。
